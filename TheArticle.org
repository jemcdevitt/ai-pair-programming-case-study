* AI Pair Programming
** Introduction

  I sometimes jokingly refer to myself as a /grey-haired neck beard/. In my case I can back that up. 

  I started programming more than forty years ago, when using a computer could literally involve punching cards and sending them somewhere else to be run. In high school, our computer lab was largely handed to me because I was one of the few people who knew what to do with it. My early professional work included C, embedded systems, and environments where memory constraints were not an abstraction. At one point I modified a home-grown C compiler so it could deal with bank-switched memory because the hardware we were targeting could address more memory than the processor could directly see. 

  Later I worked on systems used to pull consumer credit reports. The existing approach required custom code for the different report types, so I replaced much of that with a data-driven model: definitions describing the inputs, mappings used to construct the requests, and tables describing how the responses should be rendered. New report types could then be introduced largely by changing data rather than rewriting the application. Today we would simply call that data-driven development. At the time it was just the obvious way to stop writing the same code over and over. 

  From there I moved to a company managing medical rehabilitation and therapy centers. We had applications running on both Apple and PC platforms, written using completely different tool chains, and needing to support some of the early handheld computers being used by nurses and therapists. Around that time I started experimenting with a relatively new language called Java, version 1.0.2. Java solved a problem I actually had, so I kept digging.  

  We initially worked directly with Java's AWT graphics APIs, then experimented with tools from Marimba's Castanet platform. Castanet could build graphical Java applications and serialize the resulting interface, so I wrote a tool that decompiled that serialized representation back into Java source we could incorporate into our application. I also became active in the Java Usenet groups, asking questions and answering them when I could. 

  Eventually somebody at JavaSoft noticed and asked whether I would be interested in joining them. My company happened to be going through an acquisition and relocation, so I joined Sun's JavaSoft division as one of its early Java Enterprise Architects on the East Coast. 

  By then software development had become both my profession and, apparently, a very long-running experiment in learning the next thing. 

  After Sun I became Home Depot's first person with the formal title of /architect/, later moving into a director role. Over the years that followed I held architecture and engineering leadership positions at companies including a major public-records provider, Hewlett Packard, a consumer lending company, Equifax, and a SaaS platform serving small service businesses. My work ranged from large-scale application modernization and microservices to engineering leadership, security and PCI programs, and stabilizing growing software organizations. Today I work as a contract Chief Architect helping another growing company modernize its platform and engineering practices. 

  The individual technologies have changed repeatedly over those decades. What has remained remarkably consistent is the pattern: a new tool or architectural idea appears, people argue about whether it changes everything, and eventually we discover where it is genuinely useful. 

  I have usually dealt with those changes in my own way. While I'll read what others say, pro and con, I've found there's really only one way to understand the changes: I have to kick the tires and take it out for a spin.   

** The Problems Don't Really Change, the Tools Do

   Through all of this I have watched technology and software development go through repeated cycles of change.

   In the early days we used time-sharing systems: large centralized computers accessed through remote terminals.  The PC revolution moved much of that processing onto the user's desk.  As businesses needed to share data, we moved toward client/server systems, with desktop applications talking to centralized databases.  The Web then began pulling more of the application back onto centralized servers, accessed through increasingly capable browsers.

   In some ways we have come almost full circle.  We went from centralized computers accessed through terminals, to powerful standalone computers on every desk, and then back toward centralized applications accessed through what had become very sophisticated terminals. 

   The implementation details were radically different, of course, but the motivation behind each change was remarkably consistent: improve efficiency, make systems easier to support, allow information to be shared more easily, and reduce the amount of specialized work required at each user's computer.  Software development itself followed a similar path. 

   We moved from machine code and assembly languages toward higher-level languages such as FORTRAN and COBOL. Structured programming gave developers better ways to control increasingly complex applications. Object-oriented programming introduced another way to organize that complexity around objects and responsibilities.  Graphical interfaces pushed us toward event-driven programming.  The Web drove new distributed architectures and communication models.  Cloud computing later abstracted much of the  infrastructure itself, while DevOps and CI/CD attempted to make building, testing and deploying software faster and more repeatable.  

   The way developers worked together changed as well.  Waterfall development gradually gave way to more iterative approaches.  Extreme Programming, introduced in the 1990s, formalized practices such as pair-programming, where two developers work together on the same problem.  One may be writing the code while the other reviews, questions assumptions, considers alternatives and thinks ahead.  Those roles can switch constantly during the session. 

   The Agile movement expanded the larger idea: shorten the feedback loop.  Build something, test it, learn from it, adjust, and repeat. 

   Looking back across all of these changes, I see a common thread.  We keep inventing new abstractions, tools and processes in an attempt to tame complexity and give people more leverage.  Sometimes a new idea really does change the industry.  Sometimes it is mostly a new version of something we have done before.  Usually it is some combination of the two.
   
   What rarely changes is the underlying goal: do more useful work, with less unnecessary effort, while retaining enough control to understand what the system is actually doing. 

** Generative AI

   Then generative AI arrived.

   The reaction was hard to miss.  On one side were increasingly ambitious claims about AI replacing developers, autonomous agents building entire applications, and companies reducing engineering staff because software could now be generated instead of written.  On the other side were developers looking at poorly designed or poorly reviewed AI-generated code and dismissing the result as /AI slop/.
   
   Both reactions contained something real.

   AI could clearly generate useful code, explain unfamiliar APIs, summarize documentation, suggest designs, and produce working examples at a speed that was difficult to ignore.  It could also generate code that looked perfectly reasonable while being subtly wrong, unnecessarily complicated, or completely inappropriate for the system around it. 

   None of that was particularly surprising to me.

   Poor software existed long before generative AI.  So did over-engineering, bad abstractions, copied code that nobody really understood, and developers using tools without understanding what those tools were doing.  Generative AI appeared capable of producing good work faster, but it could just as easily produce bad work faster if nobody was exercising engineering judgment. 

   I also began seeing AI appear in places far beyond writing code.  Job descriptions increasingly mentioned AI experience.  Resumes were being written or screened with AI.  Interviews were beginning to include questions about AI-assisted development, while candidates were themselves using AI to prepare for those interviews. 

   Clearly something was changing.

   I didn't know exactly where I stood on it, and reading arguments for or against it was not going to answer the question for me. So rather than argue about what AI might be capable of, I decided to find out for myself. I would build something with it. 

** What Was I Trying to Build

   Most people have at least heard of Minecraft. It is a 3D open-world survival and building game, and the Java edition has developed an enormous ecosystem for extending what the original game can do. 

   There are several ways to do that. Mods can fundamentally change the game by adding new blocks, items, creatures and mechanics, but mods generally require compatible software to be installed on both the client and server. Plugins take a different approach. They run entirely on server platforms such as Paper, Spigot or Purpur and allow an ordinary Minecraft client to connect without installing anything special. Mojang has also added its own datapack and resource-pack capabilities over the years, increasingly blurring some of those boundaries. 

   I was specifically interested in the plugin approach. I wanted to see how far I could push a standard Minecraft client using only server-side code and the capabilities Mojang already provided. 

   I had three ideas.

   The first was sailable ships, a feature that has been implemented multiple times in Minecraft's history.

   One of the oldest solutions is a plugin called /Movecraft/, which allows players to construct vessels from ordinary blocks and then move them around the world. Its approach is essentially discrete movement: relocate the blocks that make up the vessel from one position to another in one of the cardinal directions. Years ago I had played with a mod called /Davinci's Vessels/, where a structure assembled into a vessel that could move and turn smoothly, much more like an actual Minecraft boat. 

   I wanted that experience without requiring a client mod.

   Mojang had recently added *Display* entities to Minecraft, and I had an idea that they might provide the missing piece. That experiment became /SimpleShips/. 

   The second idea came from wanting something interesting to do once I had ships sailing around the world. Minecraft has treasure maps, but I wanted something more adventurous. Another game I had played, /Atlas/, placed floating bottles in the ocean containing maps that led players to guarded treasure on distant  islands. 

   I wanted my own version of that idea. That became /Dead Man's Chest/.

   Finally, I wanted to see whether a plugin could effectively introduce new building geometry. Modded Minecraft has long had building systems with roof pieces, slopes and other shapes that the vanilla game does not provide. Other building games commonly offer triangular pieces, and I had often wished Minecraft did as well. 

   That experiment became /Ramps and Wedges/.

   So I had three projects, each intentionally pushing at something plugins were not obviously designed to do: smoothly moving structures, more elaborate treasure-map adventures, and what amounted to new block geometry without actually adding new blocks. 

   I had played with the plugin APIs before, but never substantially. Getting started presented another problem. The Bukkit and Paper APIs together contain thousands of classes, interfaces and enumerations, along with supporting libraries such as JOML. The documentation is extensive as API reference material but often sparse when it comes to explaining how the pieces are intended to be used together. There is also considerable history in those APIs, including functionality retained for compatibility with older versions of Minecraft. 

   I knew how to design and write the software. What I didn't know was where all the pieces I needed were hiding. 

   That was when I thought about using AI.

   A colleague had mentioned some time earlier that he increasingly used ChatGPT instead of a search engine when trying to find technical information. Rather than construct a series of searches, sift through results and piece together an answer, he could describe what he was trying to accomplish in natural language and let ChatGPT help point him in the right direction. 

   That seemed like a useful experiment in its own right. I would use ChatGPT as a research assistant to help me navigate unfamiliar APIs and find likely approaches to the problems I was trying to solve.

   What started out with me using AI as a research assistant became what can only be described as a pair-programming arrangement, one that gave me real insight into just how much power this type of collaboration can deliver.

** Could This Actually Work?

   The /SimpleShips/ plugin idea started with a question - with the newest capabilities available in the Minecraft platform, would it be possible to substitute existing blocks with new *BlockDisplay* entities, then smoothly move those around in the game?

   As I've mentioned previously, back in the Minecraft 1.7.10 days I was a big fan of the Davinci's Vessels mod where a ship could be constructed from regular blocks, then a special helm block was placed that could be interacted with.  The ship could be assembled and then move and rotate as a single vessel rather than individual Minecraft blocks.

   Entities, unlike normal blocks, are not restricted to placement on the grid boundary, and they can be rotated 360 degrees. In version 1.19.4, Mojang introduced *Display* entities that could reproduce the appearance of blocks or items with the flexibility of an entity. Normal game entities are active participants in the world, with behavior that may be updated every game tick, making large entity-heavy structures potentially expensive. *Display* entities were designed primarily for visuals and do not carry that same active behavior. Theoretically, I should be able to use these new features to replicate what Davinci's Vessels provided. I wanted to see if I was right.

** Setting Up the Collaboration

   I started the project by creating a new ChatGPT context and explaining that I would be building a Minecraft plugin for a [[https://papermc.io/][PaperMC/Bukkit]] server, using the AI primarily to help me understand the available APIs. I had already cloned a sample plugin project and wired Emacs into the Gradle build. I was using ChatGPT through the regular web interface rather than integrating it directly into my development environment, so the workflow was simple: ask questions in the chat, review the responses, and adapt what was useful into my code.

   Early on in the process, each time I'd make what I felt was a simple statement of what I was doing, the AI would generate long responses with suggested code or suggested capabilities to make use of.  When I first provided a copy of the sandbox plugin Java code, the AI returned an updated version and pointed out several things to watch out for. As an example, I had a very basic command handler in place, the AI pointed out that non-players could trigger commands and I should explicitly handle those.  It then provided me with direction on how to create new commands in the plugin's config.yml file and wire them into code. It also suggested tagging any entities my plugin created with a plugin-specific *NamespacedKey*.

At the time, that looked like just another useful implementation suggestion. Looking back, it was one of the earliest hints of a pattern that became foundational across all three plugins: let the objects created by the plugin carry their own identity and state.

** Working Prototype - Sandbox
   
   For the sandbox experiment I tried to follow the model of the Davinci's Vessels, I wanted a custom /helm/ that the player would interact with.  I had reviewed a number of datapacks that produced decorative items by creating textured /player heads/.  I provided a snippet of code from one of those datapacks to the AI and it explained the various components of the JSON.  It then identified from the Paper APIs some classes I would likely need to copy the functionality of the datapack.  I located a player head texture of a ship's helm and implemented the suggested code pattern using it.  I also set up commands that I could run from the client to give the player a helm.  I got that working, spawned in the head, attached it to an armor stand and decided I didn't like the look.  It was basically a /wheel/ attached to the side of a wooden block.

I even commented that I knew there was a capability for custom models using resource packs and thought that might be acceptable.  The AI agreed, the player head approach would never provide what I was seeking and said that the custom model + resource pack was likely the best way to go, but it did also suggest a multi-part display entity model option.  As with the early *NamespacedKey* suggestion, if this were a mystery novel these would both be considered foreshadowing events.  The AI went on to suggest a phased approach -

   As I worked through this initial phase I noted that the AI was providing standard code patterns for developing a plugin, examples of which could generally be found if someone searched for it.  That was expected knowing how the AI models are trained, but the thing I did notice was how it was providing approaches and answers to questions in mere moments.  And it was demonstrating how it could evaluate multiple possible solutions in real time and present alternatives such as with the two helm approaches. The speed I had expected, what surprised me was how quickly it could evaluate several plausible approaches and present the trade-offs between them. That felt familiar. It reminded me of whiteboarding sessions with senior architects where we would throw different approaches at a requirement and debate which one best fit the problem.

   I knew the AI could evaluate images. What I had just learned was that it could use visual feedback to influence the next design decision.  At this point the AI suggested how I should go about using the new helm, not as a placed block, but as a /control object/ that was actually built from an *ItemDisplay* and an *Interaction* connected together by an ID.  This was my first exposure to the *Interaction* and the AI continued on providing details about events that are triggered when the player right clicks one of these entities. The AI also said I needed to hook the block placement event to allow the player to place the item into the world. I now had the information I needed to create a helm, place a helm and know when the player clicked on the helm.

   There needed to be some type of feedback to the player when they clicked the helm.  Looking back to my inspiration, when clicking the Davinci helm the player would be presented with a menu allowing for naming of the ship, assembling and disassembling the ship, mounting and dismounting  the ship and aligning the ship.  I wanted something similar and had used other plugins that used the inventory interface with selectable items to trigger events.  I posed the idea to the AI and it provided direction on setting that up.  I had the same options Davinci's provided aside from naming of the ship.  Following the guidance, I added the code and now when the player clicked the helm, the inventory would open up and clicking an item triggered another event.  One thing I did notice about the AI code suggestions was that it was good at being comprehensive.

** The AI Was Looking Ahead

   What I mean by that is when it provided the approach for how to present the /menu/ and how to handle events when the player clicked an item, it also provided direction of how to prevent the inventory item from being dragged or moved.  This was obviously the behaviour that I would want for a menu like this, but I hadn't actually articulated it.  I knew AI models were trained on large collections of existing technical material, so it wasn't surprising that the response reflected common implementation patterns for this kind of menu.  This time the AI was including the little details that would eventually be necessary to have in a robust system, well before any testing showed the problem. Had I researched and built the menu myself, I’m not sure I would have thought to prevent item dragging in the first iteration. I likely would have found it during testing. In this case, the AI surfaced the edge case before I encountered it, saving a development/test cycle. It was a small example of something we used to call RAD—rapid application development—but with one more robustness detail already accounted for.

** My Experience, Augmented by AI
   
   On to the next step, ship assembly.  Here I used my own experience to implement a BFS flood algorithm to identify blocks that could be included in the assembled ship.  I already knew how to implement a standard BFS flood search: start from an anchor block, walk outward in six directions, reject blocks outside the allowed material set or ship bounding box, and collect the rest.  The code captured the *Location* for each identified block into a collection to be further processed. Here I asked the AI to do a code review of the ship assembler code and it made two recommendations that I adopted. First, it suggested that I not use the helm's position as the anchor point, but the block the helm was sitting on.  That was a real block which would ensure there was at least one block found.  The second suggestion was to not have a collection of *Location* objects as the outcome, but to define a Java /record/ that took in a *Location* and could be enhanced later as more data needed to be captured.  Things were coming together, I was now to the point of having identified a /ship/ based on a player's action.

   Now we had reached the key to my question, what happened if I replaced the real blocks with *BlockDisplay* entities?  The first thing I needed to understand was how to configure a *BlockDisplay* to look like the source block.  I had assumed it would have to do with the *Material* the block was made of, similar to how we used *Material* values with *ItemStack* objects to make the item in inventory look like what we wanted.  Turned out there was more to it.  The AI pointed me to the *BlockData* attribute of regular blocks which is basically the captured state of a block, including the correct *Material*.  A *BlockDisplay* is configured by giving it a *BlockData*.  I now understood the previous suggestion to create a /record/ to capture block information during assembly.  During the assembly operation I was now retrieving the *Location* and *BlockData* from each connected block and capturing that in my assembly record.

   For my first real test, then, all I needed to do was loop through the collection of assembly records, remove the physical block by setting its type to *Air* and creating a *BlockDisplay* using the captured *BlockData*.  This is what I did and for the first ship made up of a collection of oak planks, it worked.  Upon ship materialization, my player immediately fell through the *BlockDisplay* entities and into the water, exactly what used to happen with Davinci's.  I now had a ghost ship, I needed some way to keep the player attached to the ship, and that meant I needed a seat.

   I already knew there was a concept in the existing system of a /vehicle/ that could take entities. I was also aware that the *ArmorStand* entities could take a passenger, as this was something I had seen used in other plugins and datapacks, and when I saw that I could disable gravity on the armor stand, this is what I decided to use.  When the player would assemble the ship, I would spawn in an *ArmorStand* and mount the player on it.  Another request for a code review and the AI's next suggestion was that I should create a *Helm* class and *HelmListener* and also a *Chair* class and *ChairListener*.

** From Prototype To Structure

   Many of the suggestions being made by the AI were not always technical implementation details, but were often related to structural details.  The AI regularly recommended approaches to implementation that followed good object oriented practices such as organization into manageable components. For example, the *Helm* and *Chair* classes would own creation and destruction of the various components and entities that were part of them, the *Helm* would own the *unique identifier* for a ship, the listeners would handle the events against the *Interaction* entities, find the associated helm and hand off the event handling.  These were not novel patterns, but they were the kinds of structural decisions that kept the prototype from turning into a pile of event-handling code as it grew.

   This is also when the use of the *PersistentDataContainer* capability started to grow.  Each component that made up the helm or the chair would be tagged with the unique ID of the helm using a common key.  Any activity that pulled up one of these components would then allow tracing back to the master helm component.  This model was more like foreign keys in database records than object composition in OO programming, but it used the machinery of the API to achieve similar results. At the time, this led me to keep simple hash tables of the created helms and chairs in the plugin for convenient runtime lookup. This, in turn, provided a mechanism for me to add a cleanup command that could locate and remove helms and chairs.

** The Rotation Jungle
   
   With this refactoring in place, I was now creating a /chair/ that consisted of an *ArmorStand* and a wool block that was added to the stand's helmet equipment slot.  The problem I ran into is I was spawning this in on the same block the helm was occupying, I needed to move it away, and this is where I ran into Minecraft's legacy systems that the AI had to explain.  What I wanted to do was simply move 1 block away from where the helm was, in the direction opposite to where the helm was facing.  Minecraft has multiple different mechanisms for determining direction, depending on the situation.  There is *BlockFace* which identifies one of 19 directions (though *SELF* didn't come into play).  Then there's different types that a *BlockData* object could implement - *Directional*, *Rotatable*, *Orientable*, even a *MultipleFacing*.  And then there's the *Location* component of everything in the game, it has a /yaw/ (and /pitch/) value.  In the source code for /SimpleShips/ there is a *UtilFunctions* class, and nearly every utility function is related to block rotations.

   But the AI was able to navigate all of these variations, and for this particular situation it suggested normalizing the player's /yaw/ to the nearest cardinal direction when the helm was placed. From that single canonical facing I could derive the helm's forward direction, the opposite direction for chair placement, the vector offset for the new *Location*, and the rotation needed to keep the *ArmorStand* facing forward. All of these various rotation approaches would come into play later as more block types were allowed on the ship.

** From Components To Ship

   Next test: place the helm, open the menu, assemble the ship. The chair spawned, the player mounted it, and the physical blocks were replaced with *BlockDisplay* entities. Now I needed the reverse operation: disassemble the ship and restore the physical blocks.

   I also found that the player could simply dismount the chair and immediately fall through the virtual ship, just as happened in Davinci's Vessels. I didn't want that behavior, so I hooked the *VehicleExitEvent* in the chair listener and prevented manual dismounting. That made the menu's dismount action responsible for removing the player safely.

   It was at this point I created the actual *Ship* class as I was needing to capture many pieces of information, such as a helm, a chair, the captured source blocks, a list of *BlockDisplay* entities that were created, this ship's canonical /forward/ direction.  I did some refactoring and removed the helm and chair hash tables from the plugin, added a new one to track a ship.  The helm was still the starting point, so the *Ship* would be created at the point in time where the player placed a helm item into the world.  The *Ship* would own the unique ID and assign it to the helm and chair. I removed the separate helm and chair hash tables and replaced them with a single registry of ships.  The cleanup code could now iterate through all known ships, force them to disassemble and remove the helms and chairs.  The *Ship* would be responsible for managing all actions on the ship - assembly, disassembly, alignment, mounting and dismounting the /pilot/ and the  movement calculations.

   After the refactor, I rebuilt and repeated the test. The helm opened the control menu, assembly created the chair and virtualized the blocks, and disassembly restored the ship, removed the chair, and dismounted the player correctly.

** Can It Move

   Now for the final prototype test: could it move smoothly? I knew movement would require a recurring update loop. The AI showed me how to schedule one through the plugin API, while cautioning against running it every game tick unless I actually needed that frequency. I wired the loop so each update was sent to the known *Ships*, added temporary commands to start and stop movement, and verified that an assembled ship was receiving updates.

   The movement algorithm was pretty basic.  Since I was only doing water surface ships and not flying ships, I could treat it like traditional 2D movement. Based on the angle of rotation and speed I simply needed to calculate the delta offset changes for the X and Z locations, apply them to every *BlockDisplay* in the *Ship* and it should work.

   I did that and the initial experiment did work, mostly.

   I was using the teleport feature of the *BlockDisplays* to physically move them.  The blocks moved, but the helm and player didn't.  Oops, forgot I needed to update their locations as well, so I added that. Now the blocks and the player moved. Success.

   Next I added turning. Updating the ship's yaw was easy enough, and the next movement calculation correctly sent the displays in the new direction. But while their positions changed, the individual displays themselves did not rotate with the vessel. Gaps immediately appeared between the blocks.

** Entering the Rotation Jungle

   I gave the AI the movement code for review and it provided the explanation I needed, again related to the rotation issues.  The way I was moving the ship was by determining each block's new location and teleporting it to that spot.  What I wasn't accounting for was that the *BlockDisplay* had its own orientation state in addition to its world position.  This was also an area where the AI was particularly useful because 3D transformation math has never been one of my strongest areas.

   I now had a situation where I had a direction of movement for the ship, an existing direction of rotation for a block and I was turning the ship.  My first attempt was to simply update the /yaw/ of every display entity's *Location* with the same amount the ship was turning.

   Again, this mostly worked, the regular blocks seemed to be okay.  But when I tested a few other block types such as furnaces with defined direction, I saw they had issues.

  The AI suggested that I stop treating each captured block as having an independent world location. Instead, I should store each block's offset from the ship's anchor and express that offset through the display's transformation matrix. This was familiar territory conceptually; I had used the same approach when loading 3D models, where every component is positioned relative to a common origin.

  I then incorporated the ship's yaw into that transformation as a quaternion. With position and rotation now relative to a common anchor, moving or turning the vessel became conceptually much simpler: update the anchor and apply the shared movement and rotation relative to it.

   And it worked, mostly.

** Timing, Cloning and Sequencing

   I was noticing that every so often the virtualized ship would not appear when assembled.  When I teleported my player to world position (0,0,0), where I was initially creating the entities,  I would see the ship display blocks had been spawned in. The problem turned out to be a timing situation with the plugin, the anchor-relative transform was correct; the mistake was spawning the displays at (0,0,0) and then moving them. I discovered I could spawn them directly at the helm's location and let the transformation offsets position them correctly.

   That resolved the first issue, but then on movement the block would still have some odd placement issues.  This turned out to be caused by the fact that when I spawned the display items in I passed it the *Location* object I had retrieved from the helm, which subsequent teleport commands would update. The AI pointed out that I was effectively sharing one mutable *Location* object between multiple displays. Each entity needed its own cloned *Location*.

   Reassembly exposed another problem: some blocks, especially connected fences, did not restore correctly. The AI explained how Minecraft performs neighbor updates when blocks change, which pointed me toward the sequencing issue.

   During assembly, I was discovering a block, capturing its *BlockData*, removing the block, and then moving to the next block. Removing the first fence caused Minecraft to update the neighboring fence before I had captured its state. By the time I reached it, I was saving the already-modified version.

   The fix was simple: separate discovery from removal. First identify every block and clone its state. Then create all of the displays from that captured snapshot. Only after that should the physical blocks be removed.

   Once those gotchas were resolved, I could assemble a ship, mount the player, move and rotate the vessel, and restore it to physical blocks. Movement was still controlled through slash commands, though, and I wanted something that felt like actually piloting a ship.

** Introducing The Pilot

   I was familiar with how other plugins captured player movement through packet manipulation and Minecraft’s NMS internals. Those APIs were highly version-specific, often requiring separate implementations for different server versions. I wanted to avoid that if possible, so I asked my research assistant what alternatives existed.

   The AI directed me to a newer experimental Bukkit event, the *PlayerInputEvent* capability.  If this worked as advertised, I should get an event every time the player performed any movement action, with the *Input* object providing flags for what type of action without needing to use the NMS.

   I wired the event into the helm listener and added a simple player-to-ship mapping when a pilot mounted. When a *PlayerInputEvent* arrived, I could determine whether that player was piloting a ship and pass the *Input* state directly to the corresponding *Ship*. The ship's normal update loop then translated that state into movement and steering.

   I rebuilt the plugin, fired up my Minecraft server, mounted my ship and - it worked.

   The movement still needed tuning, but I had answered the original question: *yes, it could be done*.


** The Real Thing

   Proving that the ship could move was one thing. Turning the prototype into something I could actually use meant dealing with the details.

   One of those was restoring directional blocks after the vessel had turned. Stairs, furnaces and other oriented blocks could not simply be put back with their original state if the ship had changed direction. This was another place where I readily leaned on the AI because 3D rotation logic has never been one of my strengths. It produced utility functions for applying the ship's yaw change across Minecraft's various orientation models - *Directional*, *Rotatable*, *Orientable*, and *MultipleFacing* - which gave me a practical way to restore blocks correctly.

   Inventory was another requirement. A chest full of supplies needed to still contain those supplies when the ship rematerialized. I extended the assembly record to capture cloned *ItemStack* contents for *Containers* along with their block state. That worked for chests, barrels and furnaces, aside from another Minecraft special case I would meet again later: double chests share one inventory.

** From Prototype To Product

   I was now ready to start expanding the ship build possibilities by adding support for other block types, but the codebase was honestly a bit messy.  One area that needed rework was the lifecycle of a *Ship*.  A *Ship* was created when a helm was placed and then retained in an in-memory hash table.  If the server was bounced, the plugin would no longer have any *Ship* objects.  I wanted to avoid storing details in external configuration files if possible, so the AI suggested a rehydration.  On world startup the plugin would scan for every *Interaction* entity, see if it was one of my plugin's by checking for the presence of a persistent data value, and seeing if it was part of a helm, then reconstruct the *Ship*.  I also had to hook the chunk loading event to do the same thing.  This worked, but felt /clunky/.

   I also had come to the decision that the whole ship operational approach, the required resource pack for the helm, the menu, etc. wasn't really working for me, so I set up a new plugin project, and began refactoring the code and moving parts over to the new project.  This time around I removed the custom model helm and captain's chair.  Instead I chose to go with a multi-item model consisting of a fence post with a resized spruce trap door as the helm and seat combination.  This looked like a little stool, the player could place it where they wanted it and that is where the ship would be controlled from.

** Impact Analysis

   An interesting side benefit I hadn't expected was that, when the AI had access to the full codebase, it could often point out where a proposed change would affect other parts of the system. A change to one class might require a listener update, a constructor change, or adjustments to related cleanup code, and those dependencies were frequently identified before I reached them myself. It was effectively providing a lightweight impact analysis alongside the code suggestion.

   In my past I have headed up change control review boards and prior to any release, we would ask the delivering team to report on their impact analysis for the changes they were making. From what I was seeing in this project, giving the AI access to the full codebase substantially improved its ability to identify likely downstream effects of a change.  In a large organization, that kind of assistance could reduce some of the manual effort involved in impact analysis. This would not be a substitute for review by the teams that understand the surrounding systems, but it could speed up the process and perhaps be more comprehensive.

** Collisions
   
   After getting most expected block types working, I needed a way to handle collisions while travelling. Since I was already defining a bounding box for the ship during assembly, my first thought was to project that box forward and test for intersections. I knew that could produce false positives on ships with narrow keels and wider upper hulls, so I asked the AI whether there was a cleaner approach.

   The AI suggested something simpler: for each block about to move, calculate its destination and check what currently occupied that space. For a relatively small performance cost, this gave me an exact collision check.

   This worked splendidly. A ship with a keel in the water and a wider hull above could pass through narrow waterways without false collisions.

   This exposed another problem: a ship could become wedged where it could no longer turn or back out. The AI suggested several approaches, but I came up with a deliberately simple one: when the ship is moving in reverse, I don't perform collision checks.

   This technically allows a ship to back through terrain and could be exploited, but this was one of the places where I chose gameplay over guarding against every possible abuse. I would rather guarantee that a player can recover from being stuck than prevent someone from misusing reverse movement.

   The same philosophy is why /SimpleShips/ has no buoyancy or detailed sailing physics. Other mods and plugins already provide more realistic ship simulation. I wanted uncomplicated fun with sailing ships.

* Ramps and Wedges  
** The Idea

   The third project in this trilogy was something a little different, not directly related to the /SimpleShips/ or /Dead Man's Chest/ but usable with them.  In many other games I had played that had building as a key factor, the building parts often consisted of blocks, walls, floors, ceilings and other parts.  In almost all of these other games, the building palette also contained triangular pieces and custom roof pieces.  Being able to /round out/ builds with triangles looks good to me.  In modded Minecraft play, I regularly include mods that add roofing systems so that I can have something other than stair and slab roofs.

   I started out this exercise by literally posing an "is this possible" question.  I'm copying that original interaction with ChatGPT verbatim (typos and all) here because I think it provides good insight into how I had come to work with the AI in my development.
   
   /Have just an "is this possible" question. With latest releases of Minecraft and datapacks it is sort of possible to have custom models through a custom resource pack is required to describe those models. Assuming that isn't an issue, would there be a way to define basically 8 new block models that are "triangles"? What I mean is, could you define new models that are basically cut the block along the two diagonals so you have wedges with the point in each of the 4 corners, and do this across horizontal and vertical diagonals leading to 8 basic simple models? Then every block could provide these 8 new block shapes with standard textures thus give ability to do smooth curves in builds and ramp designs? Cherry on top would be if the ramp types could be treated like stairs for movement purposes smoothly. I've been using triangle pieces in other building games and they work quite well. I only rarely place two triangle pieces together to form a square of different materials so I think it would be find if combining 2 triangles in one space required it operate like two slabs -same material, becomes a standard block. Is this something doable?/
   
   The AI was again ready with the answer, "Yes - visually, absolutely; physically, mostly; as true new block types, not quite".  This is the type of answer to "can this be done" questions I had become accustomed to when working with other developers and architects.  The AI went on to describe the details about the Java resource-pack model system, something I was already familiar with having gone down that path originally with the /SimpleShips/ helm that I eventually abandoned because I didn't want to require resource packs.  Here, though, I knew this was going to be the requirement and was ready to fully embrace the capabilities.
   
   The AI walked through the overall concept, where it described how I would need to create the new models, map them to /carrier blocks/ or use the *BlockDisplay* approach.  It also mentioned that we could utilize existing Minecraft textures, thus avoiding needing to create new ones.  It then pointed out the main /wrinkle/ would be in collision handling because the resource pack doesn't offer a way to define new collision boxes.  For triangles, as my collaborator pointed out, they could look good but would have a full box collision if we went the carrier approach.  If we went the *BlockDisplay* approach, we would have to define our own hit box.
   
   For the ramps, though, it suggested what it described as a /very promising cheat/, that was to use a vanilla stair block as the underlying physical carrier block but make it look smooth.  This would then use standard Minecraft stair collision handling.
   
   Lastly it explained that we didn't need to create all 8 of these new models for every block, we just needed to make 8 generic geometries and generate material-specific model JSON files that reference normal block textures.  The AI proposed a build-time generator to create what was needed.  The AI's final analysis, here again verbatim,
   
   /So I would rate it:/

   /Custom visual wedges: easy-to-moderate./
   /Hundreds of materials via generation: quite feasible./
   /Placement/breaking/rotation: moderate plugin work./
   /Smooth ramp movement: feasible by borrowing stair collision./
   /True triangular collision: the hard/impractical part./

   /As a building system, though? Very doable. You could get 90% of what makes triangle pieces useful in games like Palworld without needing Minecraft itself to support arbitrary voxel collision geometry./


   After reviewing the feedback I chose to not worry about the collision issues, as the intent for this project was really more for aesthetics, so we wouldn't go with the *BlockDisplay* approach. I wondered if we might be able to get a /better/ collision option if we used as the carrier a block that wasn't a full block and had smaller hit box, such as a wall that has a hitbox of 0.5 x 0.5 or even the dragon egg which is 0.875 x 0.875.  The AI said it was something to consider but it pointed out that if we used something like a wall piece, we'd need to consider path finding because it might visually look like a wedge, but mobs would see it as a wall.  At this point I asked if it was possible to build a prototype in a datapack to test out the idea and asked the AI to generate that datapack.

** The Prototypes

   1 minute and 4 seconds later, a datapack was ready for download.  I downloaded the pack, dropped it into a test game and had triangle wedges and ramps.  I noticed some rendering artifacts which I immediately recognized as Minecraft render optimizations.  The block that I would place a wedge on considered the wedge to be a full solid block so the connecting faces were being culled by the renderer for performance reasons.  This resulted in the exposed part of the connected block having no texture giving me an x-ray view into the ground.

   We moved on next to getting the rotated versions of the new shapes so that I could test wedges and ramps in any direction.  Version 2 of the datapack was available 1 minute later.  Still had face culling issues, but this was proving out that the idea would work.  I did notice that when normal stairs were placed next to a ramp at an angle, the normal stair connecting shape changes would occur on the normal stair but the ramp remained as it was.  Under the covers, the carrier stair block was being reshaped but it wasn't visible, the ramp model was.  At this point the AI suggested instead of trying to get creative with model geometry to solve the wedge face culling issues, I look into different carrier blocks.  I made the suggestion to try using glass blocks which, because they are transparent can't have the faces of connecting blocks culled.
   
   V3 was generated, vertical ramps were still using the *Material.STONE_STAIRS* as the carrier but now we used 4 different glass blocks for each of the wedge directions, white for north west pointing, orange for north east, magenta for south east and light blue for south west.   Upon placing the wedges, success.  The connected block didn't face cull and fully rendered the connected side.  The wedge now looked like I wanted it to look.

** Limitations

   With this update we got everything working as expected so I raised the bar - how do we get this to work with any desired block types?  The current model had a serious limitation that I had seen but not yet looked into.  Up until this point, for any ramps we wanted, the block type required that it had a stair that we could use.  The wedges required 4 transparent/translucent blocks as the carriers.  What was happening was for blocks where we could have ramps, we were giving up the original stair, and we were consuming all of the glass blocks. This was not a scalable solution so I asked if it was possible to change things around.  Instead of replacing the model of the actual block with the new model, could we instead have different item models?  I had the idea from the fact that when I had one of these new /blocks/ in my inventory, it was just an *ItemStack* with a custom model texture, couldn't we do something similar with blocks?

   The AI agreed that the current approach wouldn't scale, but that we might be able to use the inventory item model idea.  The AI then pulled out the pattern that we had used in /SimpleShips/ and /Dead Man's Chest/ and suggested that what we could do was use a single carrier block for the ramp, and 4 carrier blocks for the wedges, but when rendering we would render an *ItemDisplay* that was using our new models, the same models that were allowing the items to look correct as inventory items.  The only issue now would be that both the new *ItemDisplay* and the carrier would render because the carrier physical block was still present.  To resolve that, the carrier was given a completely transparent texture.  For ramps there still had to be a physical stair block and for the wedges we still needed physically transparent blocks, so that meant losing some blocks.  For my usage, I chose to sacrifice the red sandstone stair as I rarely used that, but I did make that configurable.

   We prototyped this approach for ramps, one sacrificed physical stair block and multiple different block types as ramps and it worked.  The AI now brought up a possible concern, what this new model was doing was creating a new entity for every ramp we created and that we shouldn't assume that just because the *Display* entities didn't receive update ticks, that they were performance free.  This is where load testing needed to occur and though I did some testing and built various structures with many ramps, I wasn't stressing it enough to prove the point one way or the other.  I decided we'd continue with this model and just see how it turned out over time and monitor performance, exactly as I would do with any other system.

We continued updating and prototyping with the ramps and were able to show that I could now create ramps of block material that didn't normally have stairs but allowed navigation just like normal stairs.  I only lost the ability to use standard red sandstone stairs.

   and stored it in the *ItemDisplay* PDC.

   We continued refactoring the code, removing unneeded pieces and fixing the errors, to the point where I had to again upload the full source code and simply asked the AI to clean it all up.  With the code cleaned up I merged that into the baseline.

   One point I'd like to make here, these frequent level-settings were not an annoyance to me.  In my career I have had the pleasure of working with brilliant developers and architects.  These individuals often worked in a way that felt familiar here: give them a problem and they could produce a working approach very quickly.  The code wasn't always well structured and often multiple iterations were visible, but it would work.  I would then have to work with them and the code to clean it up into a maintainable structure, only to have the next requirement result in reworks, dead code and more cleanup needed.  The key takeaway from those situations was that at the end of the day the code couldn't just work, it also had to be supportable and maintainable, and if I had trouble following it, then I expected others would as well. That's how I thought about this interaction.

** Testing and Polish

   More QA, more polish on the ramps, little things like removing the red sandstone stair recipe from being craftable since it would be invisible if used.  Now I was starting to think about the wedges.  We had to sacrifice only one stair block for all ramp types, but I currently needed four carriers for the wedges and was losing four of the glass blocks per block type. I posed the question, could we use the same approach for wedges we were using for ramps, one set of carriers for all types.  My collaborator indicated that should work fine.  I then asked, could we use a single carrier block and not 4, and would it work if we used the naturally invisible *Barrier* block?  The AI thought that was an interesting idea, explained why it should work, then it  pointed out that there was a wrinkle. Normally *Barrier* blocks are not breakable in survival, and so our *BlockBreakEvent* might not fire.  We tested using the *Barrier* blocks as the carrier and it being a naturally invisible block, it didn't trigger face culling and didn't trigger the *BlockBreakEvent*.

   I noticed that when I held an actual *Barrier* block in my hand, that caused any placed ones to show a texture of a red circle with a slash.  That's how that block normally works, but it looked odd on my wedges.

The AI implemented a handler for the *BlockDamageEvent* to detect when trying to harvest a *Barrier* block wedge so that it could break.  It all worked.  Wedges placed without face culling issues, they had a full block collision box, harvesting them worked and the correct *ItemStack* was dropped.  We now had a full working model for any ramp types and any wedge types costing only a single placeable block, the red sandstone stair, and a block not normally available in survival, the barrier block.  And ramps and wedges were available for any block type I wanted to try.

** More Blocks

   I now requested *ResourcePackGenerator* be updated to produce needed item files for ramps and wedges for all block types.  The AI updated the code to generate the files and specify the default textures to use based on the block type.  This worked for most all of the blocks where the code assumed the texture name matched the block name.  We did run into a few cases where a block used more than one texture for all faces and where the texture name was not the same as the block name.  Another rework of the codebase and I started testing.

   For the blocks I tried they worked as expected, I now had another polish change identified.  When harvesting the blocks, they all harvested at the same speed which was a bit jarring.  Oak ramps would take just as long to harvest as stone ramps and longer than oak stairs because the real block was a red sandstone stair.  All wedges harvested at the same speed because we had one routine handling breaking the barrier block.  And harvesting particle effects didn't match the real blocks.

   We didn't make any changes on these issues as I wanted more testing, so I took the plugin to my test server and started putting it through its paces and sure enough within minutes of building a real house I hit another change - corners. I made some additional direct changes to support using block tags in the configuration file so I could add entries like *#PLANKS* and it would add all wood plank types to the list, then I made more builds and shared the images.

   I also did my first tests with using the new ramps and wedges on a /SimpleShip/.  I built a ship using some of these new shapes and it worked.  I could sail the ship and rotate and the new /blocks/ did exactly as they should have, with one exception - after moving the ship I couldn't break the blocks.

   Turned out to be a very simple problem, the *Material.RED_SANDSTONE_STAIRS* and *Material.BARRIER* were not blocks permitted to be on a ship, but /SimpleShips/ did search for any *ItemDisplay* or *BlockDisplay* or *ArmorStand* entities that were part of the ship and they were allowed.    I considered and then rejected building some type of integration between the two plugins.    The carrier blocks now properly moved with the visual *ItemDisplay* entities and I was able to properly break the blocks, but the *ItemDisplay* remained behind.  This related back to the approach where when a carrier block was broken, I was looking for an *ItemDisplay* with the ID key I had created based on the carrier block's placement location.  The carrier block was no longer at the same location so when I used its new location to create the ID, no match was found.  I decided on a simple change here, when a carrier block was broken I would simply check the exact same physical location for an *ItemDisplay* that carried a /Ramps and Wedges/ type tag in its PDC and assume that was the *ItemDisplay* to remove.

   This new change worked, the *ItemDisplay* was now also being removed, but one more issue remained - nothing was being dropped when the block was harvested.  This was again because of the location change.  Our design was still keeping track of the block type in the chunk PDC but now that the block had moved, we couldn't use the location as the data key to see what was there.  I now took another lesson from /SimpleShips/ and /Dead Man's Chest/. Since I was now utilizing an *ItemDisplay* with each placed ramp or wedge, I had an available entity PDC to work with.

   I started down the path of dropping the chunk data store and using the *ItemDisplay* PDC which had a ripple effect on other parts of the code.  As I explained the different changes, the AI did what it had shown me previously, it performed immediate impact analysis across the codebase pointing out all areas I'd need to update. My code reviewer pointed out some additional points to handle but approved the merge.

   I was back now to some polish, specifically the issue that when breaking ramps I was seeing particles, albeit with the default magenta/black texture, but when breaking wedges I wasn't seeing any because we really weren't breaking the barrier blocks.  The AI suggested a simple function to add to the custom break handler we were using and it worked, I now had particles and they were textured right.  I realized I could get the right textures when breaking ramps if I used a custom break handler like the code was doing with wedges, but I decided not to do that for now.  Perhaps later, for now I was now playing with the code, trying different tricks to hide when there were missing faces, but in the end I decided there weren't any tricks I could use so I would just need to adjust my build approaches to avoid the situation.  This will be documented when I publish this plugin.

** Missing Pieces

   Now I was ready for the additional pieces of the roof, hips and valleys to handle the corners.  The AI made this comment

   /The nice part is that the current architecture makes adding them comparatively cheap now. They’d just be more BlockShape values with generated item models and ItemDisplay geometry./

   It pointed out that the only real issue would be the collision box.  I kept testing and added stripped wood to my list of available block types and they didn't work.  Turned out we had hit the expected issue where the *ResourcePackGenerator* was creating the texture name from the block name and it didn't match.  While the block was a *Material.STRIPPED_OAK_WOOD*, the texture it used was /stripped_oak_log.png/.  I did a quick update to check if the block type ended in /_wood/ and if so, create the texture ending in /_log/.  That worked for all wood types. Now I was ready to try adding the hips and valleys and asked the AI to do that.

   The bulk of the work was going to be creating the correct model geometries and deciding on carrier blocks.  I chose to go with using the barrier blocks for the corner pieces instead of a stair carrier for two reasons.  First, because the *Barrier* itself had no normal rendered geometry, it avoided the face-culling problem I had seen with other carriers.  And second, if we used stair blocks the Minecraft engine would alter their geometry to connect them and when that happened, they no longer looked like my blocks.  Using the barrier meant they wouldn't have the stair climbing interaction, but I decided that was an acceptable trade-off.  The end result of this new feature: only two new templates to be processed by the *ResourcePackGenerator*.  The AI produced the JSON files for stone hips and valleys for me to test with.  After I manually updated the resource pack with the new files I tested and they turned out to be smaller than regular blocks.  This was because we hadn't wired these into the stonecutter and I was summoning them as items, which were smaller by default.  They were looking pretty good with this manual testing so I uploaded another full copy of the source code and asked the AI to wire these two new pieces into the baseline.

   Three minutes and fifteen seconds later and I had another download to merge, refactoring was growing in time.  I built the new plugin, started the server, grabbed the generated resource pack and it looked amazing.

* Epilogue

   The AI started out as my API expert, my research assistant, and my sounding board when I was building /SimpleShips/.  It augmented my coding where I needed help, such as in the matrix math space and it always provided multiple options that made me stop and evaluate.

   When I started /Dead Man's Chest/, I was relying less on the AI for basic coding knowledge and more on creative solutions.  I had a vision for how this plugin should work and feel, I knew visuals would be key and that I would be dealing with more /states/ than previously. /Dead Man’s Chest/ shifted the balance. I needed less help with basic plugin mechanics and spent more of our conversations evaluating design and architectural choices. In several cases, particularly around persistence, I preferred a simpler object-owned model over the external state-management approaches the AI initially proposed.

   Then coming into the /Ramps and Wedges/, I already knew the shape that plugin would eventually take, I knew that custom models could be used to give custom looking blocks.  I also knew that it would have taken me weeks to figure out those model details, if I ever did, so I was happy to hand the bulk of the work to my collaborator.  The coding was still a joint effort with both sides doing various refactoring, but this project was almost purely visual, not my area of expertise.  The division of labor felt similar to a game-development team, where artists create the assets and developers wire them into the system.
   
   Circling back around to the introduction where there were two sides in the AI debate, those that believe it is possible to replace all development with AI code and those that see all AI code as /slop/, I've come to appreciate that both sides are both right and wrong.
   
   My journey has shown me that AI can replace a surprising amount of work. What I did not find it could replace was engineering judgment and accountability.  The AI behaved like an extremely fast researcher with broad recall. It could take a request, scan a wide solution space, and quickly point toward code, APIs, or tools worth exploring.  But it also showed me that useful results still depended on guidance, context, testing, and judgment.  The AI’s suggestions were usually plausible. But plausible is not the same thing as correct, and every meaningful result still had to survive testing in the actual runtime. The suggestions did not always account for the non-technical concerns that matter in a long-lived system: supportability, maintenance, coupling, operational complexity, and product tradeoffs. On more than one occasion I chose a different path, not because the suggested approach was technically invalid, but because I was weighing complexity, supportability, and maintenance. At times I made choices I knew would be trade-offs, but like any good product owner, I accepted those trade-offs.  Sometimes /good enough/ is truly /good enough/.

   I also think there is some merit to the /slop/ opinion, though I think it is wrong to reactively apply that to all code.  As I learned, I never actually accept the first code produced, much like in my entire career. Even though I might have joked with my team that if /it compiles, great, ship it/, that has never been true.  So taking a first pass of AI generated code and trying to deliver that as a finished project could honestly be /slop/.  But the same is true of taking any first cut of code.  Iterative development came about and is arguably the most widely used development model today because we all recognized that it is the best model for /getting it right/.

   This leaves me with the understanding that both camps are both right and wrong, that AI is a tool that when used properly, as with any tool, is a force multiplier.  Will AI impact the labor market? I think so. Near-term disruption seems likely, while the longer-term balance is much harder to predict.

   Back when the use of the internet was exploding, during the dot-com craze, we were treated to stories of how small teams in a garage were creating valuable businesses.  Today many solo developers produce phone apps that become popular.  What this means for employment is harder to predict. My experience does make me think smaller teams will be capable of work that once required larger ones. History has many examples of where a new tool shows up, it reduces the labor needs, some people are impacted, others profit, but eventually things settle down to a new normal and after the hype winds down, and the tool is being used for real world work, then ideas and new opportunities show up.

   After all of this, what surprised me most was not how much code the AI could produce. It was how familiar the working relationship felt. I had spent years at whiteboards with architects and senior developers, throwing out ideas, challenging assumptions, and leaving with a clearer idea of what to build next. The tools changed again. The engineering process did not.
